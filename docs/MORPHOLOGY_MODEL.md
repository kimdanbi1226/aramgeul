# 아람글 형태소·문법 조건 모델 초안

## 목적

띄어쓰기와 활용형처럼 문맥과 문법 기능에 따라 결과가 달라지는 규칙을 단순 문자열 치환으로 처리하지 않고, 형태소·품사·문법 기능을 입력 조건으로 사용할 수 있도록 한다.

## 1. 분석 파이프라인

입력 문장
→ 문장 분리
→ 형태소 분석
→ 품사/형태소 후보 생성
→ 문법 기능 추론
→ 규칙 조건 매칭
→ 규칙 충돌 해결
→ 교정 후보 생성
→ 근거 연결
→ 결과 상태 결정

## 2. 토큰 모델

각 토큰은 최소 다음 정보를 가진다.

| 필드 | 설명 |
|---|---|
| text | 원문 표면형 |
| normalized | 내부 비교용 정규화 형태 |
| lemma | 기본형 후보 |
| pos | 품사 |
| morphemes | 형태소 목록 |
| features | 활용·문법 형태 정보 |
| start/end | 원문 위치 |
| confidence | 분석 신뢰도 |

## 3. 형태소 모델 예시

'할 수 있다'는 내부적으로 다음과 같이 분석할 수 있다.

- 할 → 하/VV + ㄹ/ETM
- 수 → 수/NNB
- 있다 → 있/VX + 다/EF

핵심은 표면형 '할수있다'만 보는 것이 아니라, 분석 결과에서 '수'가 의존 명사임을 확인한 뒤 띄어쓰기 규칙을 적용하는 것이다.

## 4. 문법 기능 태그

필요한 경우 품사만으로 부족하므로 별도의 기능 태그를 둔다.

- JOSA
- DEPENDENT_NOUN
- AUXILIARY_VERB
- NEGATIVE_ADVERB
- LEXICAL_VERB
- ENDING
- MODIFIER
- BOUND_MORPHEME

## 5. 문맥 의존 규칙

다음 유형은 형태소 분석 결과와 주변 문맥을 함께 사용한다.

- 만큼
- 뿐
- 밖에
- 데
- 지
- 시
- 안
- 못
- 되다
- 보조 용언
- 조사/의존 명사 동형 표현

예:

'나만큼'
→ 체언 + 조사

'할 만큼'
→ 관형사형 + 의존 명사

따라서 동일 문자열이 포함되어 있어도 다른 규칙이 적용된다.

## 6. 활용형 처리

'되다' 계열은 활용 어미를 분석해야 한다.

- 되 + 어 → 되어 → 돼
- 되 + 어요 → 되어요 → 돼요
- 되 + 나 → 되나
- 되 + ㄴ다 → 된다

따라서 '되/돼'는 문자 교체 규칙으로 만들지 않는다.

## 7. 부정 표현 처리

'안'은 다음처럼 구분한다.

- 부정 부사 '안' + 용언 → 띄어쓰기 후보
- 한 단어 '안되다' → 사전 의미와 문맥을 함께 확인

예:
- '안 돼요' → 부정 부사 + 되다
- '공부가 안돼요' → 한 단어 '안되다'의 활용 가능

따라서 '안' 뒤를 무조건 띄우거나 붙이는 규칙을 만들지 않는다.

## 8. 불확실성 처리

형태소 분석이 여러 후보를 내거나 문맥이 부족하면 규칙을 강제로 적용하지 않는다.

예:

analysis_confidence: low
decision: AMBIGUOUS

이 경우 교정 후보를 제시하더라도 확정 표현을 피하고 필요한 문맥을 요청하거나 근거를 함께 표시한다.

## 9. 엔진 인터페이스 초안

{
  "text": "할수있다.",
  "tokens": [],
  "candidates": [],
  "decisions": [],
  "sources": []
}

규칙 엔진은 형태소 분석기를 직접 소유하지 않고, 표준화된 분석 결과를 입력으로 받도록 설계한다. 이를 통해 나중에 형태소 분석기를 교체해도 규칙 엔진을 크게 수정하지 않도록 한다.
